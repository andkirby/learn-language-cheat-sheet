Foundations

Type voices

Two voices, one rule: Russian explanation text uses --font-ui (system sans); any element carrying the studied language is marked with a lang attribute and rendered in --font-study (system serif) — the “this is the language you are learning” signal.

RU explanation — sans --font-ui

Предлог часто сразу определяет падеж: спроси Wo? или Wohin? перед Wechselpräpositionen.

auf dem Tisch (Wo?)
auf den Tisch (Wohin?)
Ich gebe dem Kind das Buch. — Wem? Dat. · Was? Akk.

Line 1: mixed RU/DE — only the German fragments carry lang="de" (bold). Line 2: pure German — the whole .example container is marked, so the full sentence takes the study voice and stays readable as one unit.

Marking rules, fonts, and what must never take the serif

Pages set lang via markTargetLang in the page script (see page_template.html): whole .example / .answer / .table-scroll containers are marked when they contain no Cyrillic; otherwise the fragments are marked — bold in .example/.answer, italics in .detail-block, and formula slots without Cyrillic individually.

lang does two jobs: the serif study voice ([lang] selector in base.css) and screen-reader pronunciation. Never apply it to Russian text — that would flip the explanation into the study voice and mispronounce it.

Stacks (no external fonts): --font-ui = system sans; --font-study = Charter → ui-serif (New York) → Sitka/Cambria → Noto Serif.

Color tokens

Semantic roles only — raw hex lives exclusively in the :root blocks of base.css. Every light value ships with its dark twin (≥ 4.5:1 for text). Toggle the theme in the topbar to check both.

--bg · page
--surface · cards, topbar
--surface-2 · examples, th
--text · body
--muted · secondary
--line · hairlines
--accent · focus, info
--accent-soft · chips, active nav
--on-accent-soft · on accent-soft, td.hot
--ok / --ok-soft · verb slots, answers
--warn / --warn-soft · end-of-sentence slots
--hero-1/-2… · landing hero only

Non-color tokens: --grab, --backdrop, --shadow, --radius, --nav-h, --font-ui, --font-study.

Token governance

New color need → add a semantic token to base.css first (light + dark together, dark ≥ 4.5:1 for text), then use it. Never reuse a primitive for a second meaning; never put raw hex in component rules or page styles — the only exceptions are the :root blocks and black-key shadows. The theme-color metas must match the light/dark --bg values. The full role table with hex values lives in .design/DESIGN_SYSTEM.md; this page shows the roles, that file owns the numbers.

Search behavior & menu contracts

Search. Cards match on card.textContent + data-search (lowercased substring). While searching, body.searching is set (the noscript intro hides), matching sections from every view stack into one result list, #noResults shows at zero matches, and clearing restores the active view. Search never destroys dialog or answer state. data-search is a designed surface: deck authors put the hidden keywords there (forms, Russian prompts) — findings C-11–13 came from treating it as an afterthought.

Language menu. Native <details> keeps it functional without JS; JS adds light dismiss and Escape. On deck pages it sits in the search row (the brand row can't fit it beside the install button at 390px); the landing has it in the brand row. Driven by content/decks/site.json on deck pages and mirrored by hand in index.html — update both when adding a language or audience.

Block registry: deck JSON key → markup (and the visual order)

Each card is a list of blocks; the registry (tools/deck_blocks.py) owns each type's markup, and one block per card wins. Visual order is fixed by HTML_ORDER, not JSON order: h → p → tiny → example → formula → table → chips → notice → detail.

Card density rules

First layer = trigger + rule + one short example (DESIGN_SYSTEM: “compact reference cards, not a textbook”). Everything deeper is a .tap chip into a DETAILS entry. Examples ≤ 2 lines; bold marks pattern-carrying words. Card content feeds search automatically via textContent; anything that must be findable but isn't visible goes into data-search.

Badges. Optional card-root level (A1/A2/B1) and kind (what the card gives you — формы / употребление / порядок / время / связь / условное / триггер) render the .badges row under the title. The build validator enforces the level enum and a 1–40 char kind, and rejects both on case-grid cards. Every badge carries a text label — never information by color alone.

Pairs. An example block with an optional gloss (runs) renders as .example.pair: the target-language .pair-src line takes the study voice and .hit marks the form the card teaches; the audience-language .pair-gloss stays in the UI voice under a hairline. Glosses follow the gloss policy (SITE_PLAN_GUIDE §6): deciding hints, not translations.

Tappable chips

The only button styles on language pages. Open a DETAILS dialog or reveal an answer. Visual min-height 40px with ::after hit-area expansion to ≥ 46px — density without missed taps.

.tap primary · .tap.neutral secondary · .tap.case 44px case tile. No other button styles.

Why min-width lives on the table, not the container

table { min-width: 560px } is what forces the scroll inside .table-scroll; grid items are allowed to shrink (.cards > * { min-width: 0 }) so the card never overflows the page. Print undoes both (overflow: visible; min-width: 0). The ~390px no-page-overflow check in AGENTS.md exists to guard exactly this pair.

Overlays & navigation

Bottom-sheet dialog

One shared #detailDialog per page; content set from the page’s DETAILS object. Closes via ×, Escape and backdrop tap. Focus is trapped natively by showModal().

DETAILS shape & dialog markup 
<dialog id="detailDialog" aria-labelledby="detailTitle">
  <div class="sheet">
    <div class="grab" aria-hidden="true"></div>
    <div class="sheet-head">
      <div><h2 id="detailTitle"></h2><p class="lead" id="detailLead"></p></div>
      <button class="close-sheet" id="closeDialog" …>×</button>
    </div>
    <div id="detailBody"></div>
  </div>
</dialog>

DETAILS[key] = {title, lead, body}; body is pre-rendered from the deck's details[key].blocks as a run of .detail-block divs (<b>label</b> + runs, italics take lang). Backdrop close relies on event.target === dialog. The install button reuses this dialog for its iOS/generic how-to (INSTALL object).

Bottom nav & views

Five view destinations; the selected view is the nav truth (aria-current), no scrollspy. Sections carry data-view; legacy anchors open the section’s view first. While body.searching is set, matching sections from every view are shown stacked. Shown here as a static specimen (.sg-nav override).

Real pages: fixed to the bottom, respects env(safe-area-inset-bottom). Views/destinations/legacy anchors are owned by each language plan, not by this contract.

View switching, hashes, and print

A nav tap: clears an active search (predictable destination), pushes #viewId, shows that view's sections (hidden on the rest), sets .active + aria-current="true", scrolls top. Hash handling: section ids win (open their view, scroll to the section — the legacy-anchor path), view ids switch views; unknown hashes keep the current view. Initial load honors a deep link. Noscript and print show everything stacked (section[data-view] forced visible in print).

What is deliberately NOT in base.css

The landing hero and .lang-card live inline in index.html (hub-only components), and each language page owns nothing beyond the shared stylesheet. The card badges and example pairs above started as page-local ux-* proposals in research/ui-improved-example.html; adoption promoted them to base.css (see #research for what is still deferred).

Do / don’t

Do

· New color → semantic token in :root first, light + dark together.

· Keep touch targets ≥ 44px effective (hit-area padding allowed).

· Depth goes into DETAILS dialogs; first layer stays one screen.

· Mark target-language text with lang — it drives pronunciation and the study voice.

· Bump CACHE_VERSION after any cached page/asset change; keep anchors stable.

· Record contract changes in .design/decisions.md and roll them out to every page in one commit.

Don’t

· Raw hex in component rules or page-local overrides of base.css.

· user-scalable=no or unconditional maximum-scale=1.

· Information by color alone (pair td.hot-style cues with weight/text).

· New button styles beside .tap, or hero/jump-chip style navigation.

· Behaviors that die without JS — noscript must still read the whole deck.

· Submenus in the language menu — flat groups only, both choices visible.
